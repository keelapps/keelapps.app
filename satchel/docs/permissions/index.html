Permissions Satchel requests, and what runs as you

What runs as you

Every attachment read and every deletion runs as you, with your own Atlassian identity. If you cannot open a file in Jira, Satchel cannot hand it to you, and that includes attachments on issues hidden by issue security. (Jira does not restrict an attachment added in a restricted comment: anyone who can view the issue can open it, in Jira and in Satchel.)

The one exception is the background project inventory, which runs as the app because a queued job has no signed-in user. Its rows are filtered to what the reader can see every time they are read.

Scopes

ScopeWhy
read:jira-workread issues, run JQL, read attachment metadata and attachment content, which is how the app finds and downloads files
read:jira-userlook up display names for account ids, as you, when a screen shows one (uploaders in an inventory, people in an audit record); names are not stored
write:jira-workheld only because deleting an attachment needs it; the only write call in the code is DELETE /rest/api/3/attachment/{id}
storage:appscan records, audit records and settings, in Atlassian-hosted storage on your own site

About the write permission

write:jira-work is broader than what Satchel does with it. Atlassian's consent text for it mentions creating and editing issues, posting comments, creating worklogs and deleting issues. Satchel does none of those things, and never uploads anything. It is the only classic Jira scope that includes deleting an attachment (the granular scope that would say exactly that is still in beta), and a test in the build fails if any code path reaches a mutating call other than the single attachment delete.

There is no permissions.external block, so the app cannot make an outbound call, which Atlassian enforces at the platform level.
