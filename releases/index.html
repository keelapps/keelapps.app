Releases for Bitbucket

For the tag that says nothing about what shipped

A tag should say what shipped, and who approved it.

GitHub has had release pages since 2013. In Bitbucket Cloud a tag is still a name on a commit. Releases for Bitbucket turns every tag into a release: its notes from git, the pull requests it brought with who approved them, whether it built, and its files in Downloads. Export any release as Markdown or JSON. Nothing to configure, and nothing leaves Bitbucket.

The gap this fills

BCLOUD-11404 — attach release notes and artifacts to tags, like GitHub Releases — has been open since 2015. Bitbucket Cloud can compare two tags, but it has no page for a release: no notes, no approvals, no files.

So a release lives in a wiki page someone writes by hand, a changelog nobody links, and a Slack thread. When an auditor asks who approved what went out in 2.3.0, someone spends an afternoon in the commit log.

Capabilities

What it does

Every tag, as a release

A Releases page in the repository sidebar, newest first, with the latest final release and pre-releases marked, and a Latest release card on the Source page.

Notes from git, not from the app

The annotated tag's message, or the version's section of CHANGELOG.md at the tagged commit. Nobody can edit them in the app afterwards.

What changed since the last release

The pull requests in the release with their authors, approvers and Jira work item keys, and every commit that went in without one.

The evidence behind it

Which pull requests someone else approved, which were merged by their own author, whether the tagged commit built, and every Code Insights report on it.

Its files, from Downloads

The files in Downloads whose names carry the version, so a release shows its build output without anyone attaching it by hand.

Markdown and JSON export

Copy a release as Markdown for a wiki page, a customer or a change ticket, or as JSON for an audit file.

On the release

Every pull request since the last tag

Walkthrough

From a tag to a release anyone can read

  1. Install the app on your workspace

    Install it as a workspace administrator. Every repository gets a Releases page and a Latest release card. There are no settings.

  2. Tag the way you already do

    git tag -a v1.4.0 -m "…", or a section for 1.4.0 in CHANGELOG.md. Tags you pushed years ago are releases too.

  3. Open Releases in the sidebar

    Each release has its notes, its pull requests and approvals, its build and reports, and its files.

  4. Export it

    Paste the Markdown into Confluence or a change ticket, or file the JSON with your audit evidence.

Limits

Limits we state up front

It shows what git and Bitbucket recorded. Notes you never wrote are not invented: a tag with no message and no changelog section shows its pull request titles and says so.

Tags, not a release workflow. It does not create tags, draft notes or upload files. Your pipeline and your git habits stay as they are.

Big releases are cut short. A release reads up to 500 commits and 60 pull requests, and the newest 1,000 tags are listed. Past that, the page says so.
